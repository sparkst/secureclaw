# IDEATION: SecureClaw Report Redesign for Non-Technical Users

## Concept

**One-sentence pitch:** Replace the dense, tabbed SecureClaw HTML report with a single-page, action-oriented summary that tells Lauren exactly what is wrong and what to do -- no tabs, no filters, no jargon.

The current report was built by engineers for engineers. It has a Dashboard tab, a Findings tab with five filter dropdowns, a Security Posture tab, CSV export, type-ahead search, confidence percentages, triage badges, auto-fix badges, context badges, severity codes, and code blocks with copy buttons. Lauren does not care about any of this. She opened a file, got scared, and closed it.

**JTBD (Jobs-to-be-Done):** Lauren is hiring this report to answer three questions:
1. "Am I safe?" (yes/no -- a 2-second answer)
2. "If not, how bad is it?" (plain-English summary, not a data table)
3. "What do I do about it?" (one clear next step, not a 4-step CLI tutorial)

Everything in the report that does not serve one of those three questions is noise for Lauren.

## Target Users

**Primary: Lauren (non-technical TV/film producer)**
- Received files from a freelancer or collaborator and wants to know if they are safe to open with AI tools
- Has zero tolerance for CLIs, terminal commands, or developer jargon
- Makes decisions based on "red/yellow/green" signals, not percentages
- Will forward the report to her IT person if action is needed
- Likely viewing on a MacBook in Chrome or Safari

**Secondary: Lauren's IT contact**
- Needs the technical detail, but only on demand
- Wants to know which files, which lines, and how to fix
- Fine with the current level of detail, but accessed via a drill-down -- not the default view

## Core Features (MVP)

### 1. Single-page verdict (no tabs)
Kill the tab bar entirely. The report is one scrollable page with progressive disclosure. The first screen is the verdict. If Lauren needs to scroll further she can, but most Laurens will not.

### 2. Traffic-light verdict card
The current verdict card is good but buried under a header bar, tab bar, and stat grid. Make it the hero. Full-width, large icon, large text:
- **Green:** "Your files look clean. No action needed."
- **Yellow:** "We found [N] things worth a quick look."
- **Red:** "We found [N] issues that need attention."

No percentages. No counts of "suppressed" items. No "patterns checked."

### 3. Plain-English findings list (act_now and review only)
Below the verdict, show findings as simple cards. Each card has:
- **File name** (not full path -- just the filename, with folder on hover)
- **What we found** (one sentence, no code blocks)
- **What to do** (one sentence, e.g., "Send this file to your IT contact" or "Delete this file and request a clean copy")
- **Severity indicator** (red dot or yellow dot -- that is it)

Suppressed findings are hidden by default. No badges, no confidence gauges, no triage labels, no pattern names.

### 4. "Share with IT" button
Replace the CLI fix instructions with a single button: "Share this report with your IT team." This copies a shareable summary (or opens a mailto: link) that includes the technical detail IT needs.

### 5. Expandable technical detail
Each finding card has a "Show details" toggle that reveals the full technical info: file path, line number, matched text, pattern name, confidence, remediation steps. This is the current finding card content, available for IT but hidden from Lauren.

### 6. Remove all filters, search, and export
Lauren will never filter by category, search by pattern name, or export to CSV. Remove the entire toolbar. If the IT persona needs these features, they get them in the expandable detail or via the JSON report.

### 7. Posture section as a simple checklist
If posture checks exist, show them as a plain checklist at the bottom:
- [checkmark] Claude Code: Secure
- [warning] Cursor: Needs attention -- [one-line recommendation]

No grid layout, no stat cards, no "Informational" count.

## Non-Goals (v1)

- **Interactive fix-it wizard.** Lauren should not be running CLI commands. Auto-fix is a power-user feature for the JSON/CLI workflow.
- **Real-time scanning UI.** The report is a static HTML file. Keep it that way.
- **Multi-language support.** English only for v1.
- **Print stylesheet.** Nice to have but not MVP.
- **Dark/light mode toggle.** Ship dark mode only (matches current brand). Revisit if beta testers ask.
- **PDF export.** The HTML file is self-contained and printable. That is sufficient.
- **Detailed onboarding or education.** The report is not a tutorial. Link to docs if needed.

## Tech Stack Recommendation

No stack change required. The report is generated by `html_report.py` as a self-contained HTML string with inlined CSS and JS. The changes are purely to the template output:

1. **Remove the tab bar and tab-panel switching JS.** Replace with a single scrollable page.
2. **Simplify the CSS.** Remove ~40% of it (toolbar, filter, posture-grid, tab styles).
3. **Rewrite `_render_findings` to produce the simplified card format** with a `<details>` element for technical drill-down.
4. **Rewrite `format_html_report` to output a linear page** instead of three tab panels.
5. **Add a "Share with IT" mailto: link generator** (5 lines of JS).

Estimated effort: **3 SP** (coding). Straightforward template refactor, no new dependencies, no architectural changes.

## Competitive Landscape

| Tool | Report Style | Lauren-Friendliness |
|------|-------------|---------------------|
| **Snyk** | Dashboard with vuln cards, dev-focused | Low -- requires understanding of CVEs and dependency trees |
| **Semgrep** | SARIF/JSON, rendered in IDE | None -- purely developer tooling |
| **GitHub Secret Scanning** | Email alerts + dashboard | Medium -- simple alerts but requires GitHub familiarity |
| **Have I Been Pwned** | Single yes/no answer with plain-English detail | High -- gold standard for non-technical users |
| **SecureClaw (current)** | Tabbed dashboard with filters | Low -- looks like a developer tool |
| **SecureClaw (proposed)** | Single-page verdict with progressive disclosure | High -- aims for Have I Been Pwned clarity |

The opportunity is clear: no AI security scanner produces a report a non-technical person can understand. SecureClaw can own that niche.

## Business Model

No change to business model. This is a UX improvement to the existing free/open-source report output. It directly supports the beta tester retention goal: if Lauren cannot understand the report, she stops using SecureClaw, and we lose our best non-technical signal.

The "Share with IT" feature has a secondary business benefit: every shared report is organic distribution to a technical buyer who might adopt SecureClaw for their organization.

## Detected Plugins

- **html_report.py** -- the sole file that needs modification (lines 1-900+, self-contained HTML generator)
- **core/models.py** -- data models (Finding, PostureCheck, ScanResult, Triage) are unchanged; we consume the same data differently
- No external dependencies. No build step. No framework.

## Open Questions

1. **Should we keep the current report as a "Technical Report" mode?** We could add a `--report-mode simple|detailed` flag to `secureclaw scan`. This preserves the engineer experience while defaulting to Lauren-friendly. Cost: ~1 SP extra.

2. **What is Lauren's actual next step when she finds a red finding?** We assumed "forward to IT" but Lauren may not have an IT contact. Should we offer a Sparkry AI remediation service link? (Business decision, not technical.)

3. **Should suppressed findings be shown at all?** Current report shows them dimmed. For Lauren, even seeing "12 suppressed" causes anxiety ("suppressed sounds bad"). Recommendation: hide them completely and mention the count only in the IT detail view.

4. **Do we need a "Scan Again" button?** Lauren opened the HTML file in a browser. She cannot re-run a scan from there. But we could link to the SecureClaw app (if she has it installed) or show instructions for the GUI app.

5. **Mobile viewport.** The current report has responsive CSS but Lauren is almost certainly on a laptop. Do we need to optimize for phone? Probably not for v1, but the simplified layout will be inherently more mobile-friendly anyway.
